# Paxos Algorithm – Detailed Working

## 👥 1. Roles in Paxos
1. 🔹 Proposer
Proposes a value
Initiates consensus

2. 🔹 Acceptor
Votes on proposals
Decides acceptance

3. 🔹 Learner
Learns final decided value
Important:
A node can be:
- Proposer + Acceptor + Learner

## 🧠 2. Majority Concept
Requirement:
- Consensus needs majority of acceptors
Example:
| Total Nodes | Majority |
| ----------- | -------- |
| 5           | 3        |
| 6           | 4        |
- Key Insight:
Majorities always overlap
- Why important?
Prevents conflicting decisions

## 🔗 3. Overlapping Majority Property
- Example:
    - Proposal A → accepted by 3 nodes
    - Proposal B → accepted by 3 nodes
- 👉 At least 1 node is common
- Result:
    - Conflict resolved automatically

## 🔢 4. Paxos State (Epoch / Proposal ID)
- Each proposal has unique ID (IDp)
- Purpose:
    - Ensure ordering of proposals
- Example:
    - PREPARE(50)
    - PREPARE(100)
- 👉 100 overrides 50

## ⚙️ 5. Two-Phase Paxos Protocol
1. Phase 1: PREPARE – PROMISE
2. Phase 2: ACCEPT – ACCEPTED

## 📩 6. Phase 1: PREPARE & PROMISE
1. Step 1: Proposer sends PREPARE(IDp)
PREPARE(100)

2. Step 2: Acceptor checks:
If already promised higher ID → ignore
Else → send PROMISE
- PROMISE means:
"I will ignore proposals with ID < IDp"
- Important:
- Acceptor may also send:
Previously accepted value (if any)
- 🔑 Key Outcome:
Majority PROMISE → Safe to proceed

## 📦 7. Phase 2: ACCEPT-REQUEST
3. Step 3: Proposer sends:
ACCEPT-REQUEST(IDp, Value)
- Value selection rule:
If PROMISE contains old value → use it
Else → choose own value
- Very Important Rule:
Never override accepted value

## ✅ 8. ACCEPT Phase
4. Step 4: Acceptor checks:
If not promised higher ID → accept
Else → ignore

5. Step 5: Send ACCEPTED(IDp, Value)
6. Step 6:
If majority accepts → CONSENSUS ACHIEVED

## 🔁 9. Handling Multiple Proposers
- Scenario:
Proposer A → PREPARE(50)
Proposer B → PREPARE(100)
- Result:
PREPARE(50) ignored
PREPARE(100) accepted
- Insight:
Higher ID dominates

## 🔐 10. Preserving Consensus Value
- Problem:
    - New proposer may try different value
- Solution:
Acceptors send previously accepted value
- Result:
New proposer forced to use same value
- Key Guarantee:
Once chosen → Value never changes

## 🛡️ 11. Safety in Paxos
- Ensures:
Only one value is chosen
No conflicting decisions
- Mechanism:
Majority overlap
Value propagation
Promise mechanism

## ⚠️ 12. Why Paxos Works in Asynchronous Systems?
- Because:
Ignores delayed messages
Uses proposal IDs
Ensures ordering
- Insight:
Old messages → Ignored
New messages → Accepted

## 🔄 13. Full Paxos Flow
```yml
Proposer → PREPARE(IDp)
↓
Acceptors → PROMISE(IDp, old value?)
↓
Proposer → SELECT VALUE
↓
Proposer → ACCEPT-REQUEST(IDp, Value)
↓
Acceptors → ACCEPTED
↓
Majority → CONSENSUS
↓
Learners → Learn final value
```

# 📌 Final Summary
Paxos = Crash Fault Tolerant Consensus
Works using:
Message passing
Majority voting
Two-phase protocol
Core Principle:
Agree on state → Agree on value → Maintain consistency
