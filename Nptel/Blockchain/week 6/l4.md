# Paxos: Safety, Liveness & Multi-Paxos

## 🛡️ 1. Safety in Paxos (VERY IMPORTANT)
- No two nodes decide different values
- How Paxos ensures Safety?
    - 👉 Using Majority Voting
- Key Idea:
    - Majority sets always overlap
- Example:
    - 3 acceptors → majority = 2
    - Any two majorities share at least 1 common node
- Result:
    - Conflicting values cannot be chosen

## ⚙️ 2. Role of Proposal ID (State)
- Maintain ordering
- Ignore outdated messages
- Rule:
    - Higher ID → Higher priority
- Effect:
    - Old proposals automatically discarded

## 🌐 3. Handling Asynchronous Network
- Messages can:
    - Arrive late
    - Arrive out of order
- Paxos Solution:
    - Use IDs + Majority → Ensure consistency
- Example Insight:
    - Even if a node receives older message first
    - 👉 It may not reach majority

## 🔁 4. Safety Case Analysis
1. Case 1: Lower ID vs Higher ID
- PREPARE(50) vs PREPARE(100)
- 👉 Nodes that promised 100 ignore 50

2. Case 2: Message Reordering
- Some nodes receive 50 first
- Others receive 100 first
👉 Still only one majority wins

3. Case 3: ACCEPT-REQUEST Conflict
- If nodes already promised higher ID
👉 They reject lower ACCEPT-REQUEST
- 🎯 Final Safety Guarantee
Only one value can reach consensus

## ⚠️ 5. Liveness in Paxos
- System eventually reaches consensus
- Problem in Paxos:
    - No guarantee of termination
- Why?
    - Multiple proposers compete
    - Higher IDs keep appearing
- Example:
    - 100 → 150 → 200 → 250 → ...
- Result:
- ❌ Paxos may run forever

## ⚖️ 6. Safety vs Liveness Trade-off
- Paxos guarantees:
✔️ Safety
❌ Liveness (not guaranteed)
- Reason:
    - 👉 FLP Impossibility Theorem
- Cannot guarantee both in async system

## 🧠 7. Majority Voting Insight
- Rule:
    - If majority agrees → value fixed
- Why works?
Overlapping ensures consistency
Prevents conflicting decisions

## 👑 8. Leader Election using Paxos
- Idea:
    - Choose one node as leader
- How?
Proposer suggests:
"I am leader"
If majority accepts
👉 Node becomes leader
- Benefit:
Reduces conflicts
Improves liveness

## 🔁 9. Multi-Paxos
- Problem:
Basic Paxos handles only one consensus
- Solution:
Run Paxos multiple times
- Concept:
Each run = one decision
Use round numbers
- Structure:
Round 1 → Value 1
Round 2 → Value 2
Round 3 → Value 3
- Application:
Blockchain (block agreement)
Databases (transaction commit)

## ⚙️ 10. Multi-Paxos Working
- Rule:
- Each round has:
Unique ID
Separate consensus
- Important:
Within same round → Only one value allowed

## ⚠️ 11. Limitation of Paxos
- Works for:
✔️ Crash Faults
- Does NOT work for:
❌ Byzantine Faults
- Example Attack:
- Node sends:
Different messages to different nodes
- Result:
👉 Paxos may fail

## 🛡️ 12. Fault Tolerance Condition
- Formula:
> Total Nodes ≥ 2F + 1
Meaning:
F = number of crash faults tolerated

# 📌 Final Summary
Paxos is a CFT consensus algorithm
Uses:
Majority voting
Unique proposal IDs
Two-phase protocol
Key Trade-off:
Safety ✔️
Liveness ❌ (not guaranteed)
