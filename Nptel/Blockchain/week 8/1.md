## 2. PBFT Communication Complexity
- In PBFT:
every node communicates with many others.
- Communication complexity:
>    O(n^2)
- Where:
    n = number of replicas
- Why Quadratic?
    - Each replica exchanges messages with many replicas:
        n×n
- So communication grows rapidly.
- Result
    - PBFT:
    works well for small/medium networks
    scales poorly for thousands of nodes

## 5. Deterministic vs Probabilistic Finality

| Feature  | Deterministic           | Probabilistic       |
| -------- | ----------------------- | ------------------- |
| Used in  | PBFT                    | Bitcoin             |
| Finality | Immediate               | Increases over time |
| Forks    | No                      | Possible            |
| Reversal | Impossible after commit | Small probability   |

## 6. Deterministic Finality in PBFT
- PBFT guarantees finality using:
    quorum agreement
    overlapping honest replicas

7. PBFT Quorum Formula
- Q=2f+1
- Where:
    Q = quorum size
    f = faulty replicas

## 8. PBFT Replica Formula
> n≥3f+1
- Where:
    n = total replicas
    f = Byzantine faults tolerated

## 9. Quorum Intersection
- Core Safety Property
- Any two quorums overlap in at least:
    - f+1 replicas.
- Since only f may be faulty:
    - at least one honest replica overlaps.
- Thus:
    - conflicting blocks cannot both commit.

## 29. Trade-Off: BFT vs PoW

| Property           | BFT           | PoW                |
| ------------------ | ------------- | ------------------ |
| Finality           | Deterministic | Probabilistic      |
| Throughput         | High          | Lower              |
| Energy Usage       | Low           | Very High          |
| Scalability        | Limited       | Better large-scale |
| Communication      | High          | Lower              |
| Validator Identity | Known         | Anonymous          |

## 30. Hyperledger Fabric Transaction Flow
- Main phases:
    Endorsement
    Ordering
    Validation
    Commit

## 31. Endorsement Phase
- Purpose
- Execute:
    smart contract (chaincode)
    business logic
    Peers simulate transaction before commitment.

## 32. Endorsement Policy
- Rules specifying:
which organizations/peers must approve transaction.
- Example:
signatures from Org1 AND Org2 required

## 33. Chaincode
- Smart contract in:
- Hyperledger Fabric
- Implements:
business rules
transaction logic

## 34. Ordering Phase
- Transactions arranged into:
global sequence
blocks
- Ordering service:
does NOT execute smart contracts.

## 35. Validation Phase
- Fabric checks:
1. (A) Endorsement Policy Validation
- Ensures:
required endorsements exist.

2. (B) Read-Write Set Validation
- Checks:
data was not modified since simulation.

## 36. Read-Write Set
- Read Set
Data read during simulation.
- Write Set
Data to be modified.

## 37. Read-Write Conflict
- Occurs when:
another transaction changes data before commit.
Conflicting transaction becomes invalid.

## 38. World State
- Latest state of ledger data.
- Examples:

asset ownership
