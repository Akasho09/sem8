# Hashed Timelock Contracts (HTLC)
- A Hashed Timelock Contract (HTLC) is a special type of smart contract used to enable secure cross-chain transactions and atomic swaps between two parties without requiring trust or intermediaries.
- HTLC combines:
    Hash Lock
    Time Lock
- to ensure that:
    either both parties complete the transaction,
    or both transactions are canceled safely.
- Main Purpose of HTLC
- HTLC is mainly used for:
    Atomic swaps
    Cross-chain payments
    Payment channels
    Lightning Network
    Blockchain interoperability
- Core Components of HTLC
1. Hash Lock
A cryptographic condition requiring a secret value.
- Working
    A user creates a secret S.
    Hash of secret is generated:
- H=hash(S)
Funds can only be claimed if the correct secret S is revealed.

2. Time Lock
Sets a deadline for transaction completion.
If the secret is not revealed before the timeout:
funds are automatically refunded to the sender.
- Basic Idea of HTLC
HTLC guarantees:
| Condition                              | Result           |
| -------------------------------------- | ---------------- |
| Correct secret revealed before timeout | Payment succeeds |
| Timeout reached                        | Funds refunded   |
- Suppose:
    Alice has BTC
    Bob has ETH
    They want to exchange assets directly.
- Step-by-Step Working
1. Step 1: Alice Creates Secret
- Alice chooses a secret:
S = random secret
- Computes hash:
H=hash(S)
- Alice sends only hash H to Bob.

2. Step 2: Alice Locks BTC
- Alice creates HTLC on Bitcoin network:
- Conditions:
Bob can claim BTC if he reveals secret S.
If timeout expires, BTC returns to Alice.

3. Step 3: Bob Locks ETH
Bob creates HTLC on Ethereum:
- Conditions:
Alice can claim ETH using same secret S.
If timeout expires, ETH returns to Bob.

4. Step 4: Alice Claims ETH
Alice reveals secret S to unlock ETH.
Now secret becomes public.

5. Step 5: Bob Uses Secret
Bob sees secret S on blockchain and uses it to unlock BTC.
Atomic Swap Using HTLC
- The process is called an atomic swap because:
    both transfers happen together,
    or neither happens.
- No partial completion occurs.
```yml
Alice (BTC)                      Bob (ETH)

   Lock BTC using H  -------->
                                Lock ETH using H
<-------- Reveal Secret S

   Bob uses S to claim BTC
```

```yml
- Important Properties of HTLC
| Property         | Description                           |
| ---------------- | ------------------------------------- |
| Atomicity        | Either both transfers succeed or fail |
| Trustless        | No intermediary needed                |
| Security         | Protected using cryptography          |
| Refundability    | Funds recoverable after timeout       |
| Interoperability | Works across different blockchains    |
```

- Important Property of HTLC
    - HTLC guarantees:
        Once the secret is revealed, the other side has enough information to complete the transaction independently.
    - This ensures:
        fairness,
        atomicity,
        no partial loss.

# Trusted Third Party (TTP) for cross-chain asset transfers
- A Trusted Third Party (TTP) in cross-chain asset transfer is an intermediary entity that facilitates and verifies transactions between two different blockchain networks.
- The TTP is trusted to:
    validate transactions,
    lock/release assets,
    maintain correctness,
    prevent double spending.
- Instead of blockchains communicating directly, both chains rely on the third party.
- Basic Idea
Since different blockchains cannot naturally trust each other, a TTP acts as a mediator.
- Working of TTP-Based Cross-Chain Transfer
    - Suppose a user transfers assets from:
        Ethereum
        to
        Binance Smart Chain.
- Step-by-Step Process
1. Step 1: User Sends Assets
- User deposits tokens into the TTP-controlled account/smart contract on Chain A.

2. Step 2: TTP Verifies Transaction
The trusted entity confirms:
    transaction validity,
    ownership,
    sufficient confirmations.

3. Step 3: TTP Executes Transfer
- TTP:
    locks/burns assets on source chain,
    mints/releases equivalent assets on destination chain.
- Simple Architecture
Blockchain A  →  Trusted Third Party  →  Blockchain B
- Example
- A centralized exchange acting as intermediary:
    User deposits BTC.
    Exchange verifies deposit.
    Exchange credits wrapped BTC on another chain.
- Characteristics of TTP Systems
| Feature             | Description                 |
| ------------------- | --------------------------- |
| Centralized Trust   | Users trust intermediary    |
| Easier Coordination | Simpler implementation      |
| Faster Verification | Central authority validates |
| Custodial Nature    | TTP may hold assets         |

## Types of TTP Models
1. Centralized Custodian
- Single organization controls transfers.
- Example
Crypto exchanges.
- Advantages
    Fast
    Simple
    User-friendly
- Disadvantages
    Single point of failure
    Hacking risk

2. Federated TTP
- A group of trusted validators collectively manages transfers.
- Example
Consortium blockchain systems.
- Advantages
    More decentralized than single custodian
    Shared responsibility
- Disadvantages
    Coordination complexity

- TTP-Based Bridge Mechanism
- Lock-and-Mint Model
- Source Chain
    Assets are locked.
- Destination Chain
    Equivalent wrapped tokens are minted.

- Advantages of TTP Approach
| Advantage                | Description                     |
| ------------------------ | ------------------------------- |
| Simplicity               | Easier than trustless systems   |
| Faster Transactions      | Centralized validation          |
| Lower Computational Cost | No complex cryptographic proofs |
| Practical Deployment     | Widely used initially           |

- Disadvantages of TTP Approach
| Disadvantage            | Description                |
| ----------------------- | -------------------------- |
| Centralization          | Requires trust             |
| Custodial Risk          | TTP controls funds         |
| Security Vulnerability  | Target for attacks         |
| Single Point of Failure | Failure affects system     |
| Censorship Possibility  | TTP may block transactions |

- TTP vs Trustless Cross-Chain Systems
| TTP-Based                     | Trustless                  |
| ----------------------------- | -------------------------- |
| Requires trusted intermediary | No intermediary            |
| Easier implementation         | More complex               |
| Faster validation             | Cryptographic verification |
| Centralization risk           | More decentralized         |

- Real-World Examples
| System            | Role                        |
| ----------------- | --------------------------- |
| Binance           | Exchange-mediated transfers |
| Coinbase          | Custodial asset movement    |
| Federated bridges | Consortium validation       |


# Consensus-Driven Data Transfer
- Consensus-driven data transfer is a method of transferring data between distributed systems or blockchains where the transfer is validated and approved through a consensus mechanism rather than by a single trusted authority.
- In blockchain systems, participating nodes collectively agree that:
    the data is valid,
    the transaction is authentic,
    and the transfer should be accepted.

- Role of Consensus in Data Transfer
    - Consensus ensures that:
    all honest nodes agree on the same state,
    invalid or malicious transfers are rejected,
    data consistency is maintained across the network.

# Hyperledger Indy identity configuration,
- Hyperledger Indy is a permissioned distributed ledger framework specifically designed for:
    decentralized identity (DID),
    self-sovereign identity (SSI),
    verifiable credentials.
- An identity configuration in Hyperledger Indy refers to the setup and management of:
    decentralized identifiers (DIDs),
    wallets,
    cryptographic keys,
    schemas,
    credentials,
    and trust relationships.

- Main Goal of Hyperledger Indy
    - Provide:
        secure digital identities,
        privacy-preserving authentication,
        decentralized trust,
        without relying on centralized identity providers.
        Core Identity Components in Hyperledger Indy
- Core Identity Components in Hyperledger Indy
| Component               | Purpose                         |
| ----------------------- | ------------------------------- |
| DID                     | Decentralized identifier        |
| Wallet                  | Stores keys and credentials     |
| Verifiable Credential   | Digitally signed identity proof |
| Verifiable Presentation | Proof shared with verifier      |
| Ledger                  | Stores public identity metadata |
| Issuer                  | Creates credentials             |
| Holder                  | Owns credentials                |
| Verifier                | Validates credentials           |

## Key Concepts
1. DID (Decentralized Identifier)
- A unique blockchain-based identity.
- Example:
> did:indy:123456789abcdef
- Properties:
    globally unique,
    cryptographically verifiable,
    self-controlled.

2. DID Document
- Contains:
    public keys,
    endpoints,
    authentication methods.
- Example Structure:
```yml
{
  "id": "did:indy:abc123",
  "publicKey": "...",
  "service": "..."
}
```

3. Wallet Configuration
- Wallet stores:
    private keys,
    DIDs,
    credentials.
- Wallet Creation Example
```json
{
  "id": "wallet1",
  "key": "strongpassword"
}
```
4. Verifiable Credentials
- Digital credentials issued by trusted organizations.
- Examples:
    student ID,
    driving license,
    employee certificate.

## Identity Configuration Steps in Hyperledger Indy
1. Step 1: Create Wallet
- Wallet securely stores:
    cryptographic keys,
    credentials.

2. Step 2: Generate DID
- A DID and key pair are generated.
- Example:
Public Key + Private Key → DID

3. Step 3: Register DID on Ledger
- Public DID metadata stored on Indy ledger.
- Ledger stores:
    DID,
    verification keys,
    schemas.
- Private keys remain local.

4. Step 4: Define Credential Schema
- Schema defines structure of credentials.
- Example:
```yml
{
  "name": "UniversityDegree",
  "attributes": ["name", "degree", "year"]
}
```

5. Step 5: Create Credential Definition
- Issuer defines:
    signing rules,
    cryptographic parameters.

6. Step 6: Issue Credential
- Credential digitally signed and sent to holder.

7. Step 7: Verification
- Verifier checks:
    issuer signature,
    schema,
    revocation status.

- Hyperledger Indy Identity Roles
| Role         | Function              |
| ------------ | --------------------- |
| Steward      | Governs network       |
| Trust Anchor | Registers identities  |
| Issuer       | Creates credentials   |
| Holder       | Owns credentials      |
| Verifier     | Validates credentials |

# Genesis Transaction
- A Genesis Transaction is the first transaction recorded in a blockchain system.
It is created during the initialization of the blockchain network and becomes part of the Genesis Block (Block 0).
- It establishes:
    the initial state of the blockchain,
    network configuration,
    initial identities/assets/validators,
    or system rules.

- What the File Contains
    - The genesis file typically includes genesis transactions defining:

| Information             | Purpose                    |
| ----------------------- | -------------------------- |
| Node aliases            | Validator identification   |
| IP addresses & ports    | Network communication      |
| Public/BLS keys         | Cryptographic verification |
| Steward identities      | Trusted governance setup   |
| Consensus configuration | Initial network trust      |
